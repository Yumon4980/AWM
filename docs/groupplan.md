# 多级程序组 —— 实现计划

> 状态：**已实现**（P1–P6 全部完成）。下面的「待定问题」已按倾向方案拍板，结论标在各条下方。
> 实际落地的结构见 `docs/design.md` 的 5.5 / 5.6 两节。

---

## 1. 目标

把当前"35 个键平铺所有窗口"改成**两级 16 键**结构：

- 一级 16 个槽位，每个槽位要么是**一个窗口**（按下直接切过去），要么是**一个程序组**（按下后进入二级）
- 二级同样 16 个键，从组内挑具体窗口
- 分组关系和顺序都靠**拖动**维护，并持久化
- `Esc` 逐级回退：二级 → 一级 → 关闭

容量：16 × 16 = 256 个窗口，远超实际需要。

## 2. 按键布局：16 键 4×4

```
1 2 3 4        ┌───┬───┬───┬───┐
Q W E R   →    │ 1 │ 2 │ 3 │ 4 │
A S D F        ├───┼───┼───┼───┤
Z X C V        │ Q │ W │ E │ R │
               ├───┼───┼───┼───┤
               │ A │ S │ D │ F │
               ├───┼───┼───┼───┤
               │ Z │ X │ C │ V │
               └───┴───┴───┴───┘
```

选这 16 个键的理由：左手主键区一个完整的 4×4 方块，物理位置和视觉网格一一对应，肌肉记忆成本最低；右手可以留给鼠标。

**影响** `src/AltTabReplacer.Core/KeyMap.cs`：`IndexToVk` / `IndexToLabel` 从 35 项缩到 16 项。
`Settings.Layout.MaxPerPage` 相应改成 16。

> ⚠️ 顺带注意：低层钩子只吞掉 `KeyMap` 里的键。从 35 键缩到 16 键后，
> `5-9 0 T Y U I O P G H J K L B N M` 这些键不再被吞掉，**搜索框第一次变得部分可用**。
> 但 `1234qwerasdfzxcv` 仍然被吞，搜索体验依旧是残的。要不要让
> 「搜索框非空时索引键让位给输入」，见待定问题 D。

## 3. 交互模型（状态机）

```
                    ┌────────────────────────────────────┐
                    │            Closed                  │
                    └────────────────────────────────────┘
                          │ Alt+Tab            ▲
                          ▼                    │ Esc / Enter / 点击 / Alt+Tab
                    ┌────────────────────────────────────┐
         ┌─────────►│            Level0                  │
         │          │   16 个槽位：窗口 or 组            │
         │          └────────────────────────────────────┘
         │                │ 按下的键对应「组」
    Esc  │                ▼
         │          ┌────────────────────────────────────┐
         └──────────│            Level1                  │
                    │   组内成员，同样 16 键             │
                    └────────────────────────────────────┘
                          │ 按下的键对应成员
                          ▼
                       切换窗口 + 关闭
```

| 状态 | 按索引键 | `Esc` | `Enter` | `Tab`/`↑↓` |
|---|---|---|---|---|
| Level0 | 窗口→切换并关闭；组→进入 Level1 | **关闭选择器** | 切到当前高亮 | 在 16 个槽位间移动 |
| Level1 | 成员→切换并关闭；无映射→忽略 | **返回 Level0**（撤销那次按键） | 切到当前高亮成员 | 在组内成员间移动 |

回答问题 3、4：

- **Q3**：`Esc` 不是全局关闭，而是**逐级回退**。在 Level1 按 `Esc` 回到 Level0，并恢复进入前的高亮项和滚动位置。再按一次才关闭。
  另外 `Backspace` 作为同义键（回退的直觉键位）。
- **Q4**：靠槽位的 `Kind` 分派。`Kind == Window` 直接激活；`Kind == Group` 转 Level1。
  **只有一个成员的组自动降级为窗口**，不让用户白按一次。

### 进入 Level1 后的渲染

不用"就地展开"，改用**下钻替换列表**：整个左栏换成组内成员，顶部显示面包屑。
理由是按键语义必须干净——展开时一级和二级的键会同时可见，`1` 到底指谁会有歧义。

```
┌─────────────────────────────┐
│ 🔍 搜索...                  │
├─────────────────────────────┤
│  1 ▸ 浏览器      [Esc 返回] │  ← 面包屑，始终显示当前层级
├─────────────────────────────┤
│  1  ▣ GitHub - Edge         │
│  2  ▣ 收件箱 - Edge         │
│  3  ▣ 文档 - Edge           │
└─────────────────────────────┘
```

## 4. 数据模型与持久化

现有 `rules.json`（`List<SortRule>`，靠 `Priority` 数值隐式表达顺序）**撑不起树形结构**。
硬塞会把 `Priority` 变成没人看得懂的魔数编码。

新增 `%APPDATA%\AltTabReplacer\layout.json` 作为**布局的唯一真相来源**：

```jsonc
{
  "Version": 1,
  "Slots": [
    {
      "Kind": "Group",
      "Name": "浏览器",
      "Members": [
        { "ProcessName": "msedge.exe", "TitleHint": "GitHub" },
        { "ProcessName": "msedge.exe", "TitleHint": "收件箱" }
      ]
    },
    {
      "Kind": "Window",
      "Matcher": { "ProcessName": "Weixin.exe", "TitleHint": "微信" }
    }
  ]
}
```

`rules.json` / `SortRule` **退化为只管排除规则**（`IsExcluded`）和用户手写的正则规则，
不再承担排序职责。`OrderMemory` 整个删除，`RuleEngine` 砍掉优先级排序那段。

> 这同时解决了上一轮遗留的失败用例：顺序不再靠 `Priority` 的 `Max()` 语义拼出来，
> 那个"同进程多窗口把彼此顶上去"的陷阱从根上消失。

## 5. 窗口标识（identity）—— 最大的难点

**这是整个方案的地基，必须先定。** 跨会话要认出"这还是上次那个窗口"，可用的线索只有：

| 线索 | 稳定性 | 问题 |
|---|---|---|
| `HWND` | ❌ 重启即变 | 不可用于持久化 |
| `ProcessName` | ✅ 很稳 | 太粗：VS Code 5 个窗口彼此分不开 |
| 窗口标题全文 | ❌ 经常变 | VS Code 换文件、浏览器换标签就失配 |
| 标题的稳定后缀 | ⚠️ 一半一半 | `xxx - Visual Studio Code` 里后半段稳定，但规则因应用而异 |

**推荐方案：分层匹配 + 组以进程为锚**

1. **组的身份锚定在 `ProcessName` 上**（稳定）。默认行为：同一进程的多个窗口**自动折叠成一个组**，
   占一个一级槽位，按下后进入 Level1 挑具体窗口。
2. **组内成员的顺序不做持久化**，每次按 z-order（最近激活的在前）动态排。
   这恰好符合直觉——组里第一个永远是你最近用的那个。
3. **用户手动建的组**（把 A 拖到 B 上）可以跨进程，存 `ProcessName` 列表。
4. `TitleHint` 只作为**同进程内排序的弱提示**，匹配不上就退回 z-order，不会把窗口踢到列表末尾。

这样持久化的只有**进程级信息**，而进程名是稳定的。窗口级的易变性全部交给运行时的 z-order 吸收。

> 代价：无法做到"这个具体的 VS Code 窗口永远固定在第 3 位"。
> 我认为这个代价值得——换来的是行为可预测、不会莫名其妙漂移。
> 如果你确实需要窗口级固定，见待定问题 A。

## 6. Q1：拖动到底是分组还是排序

### 方案：落点分区（drop zone banding）

每一行在垂直方向切成三段，**落点位置决定语义**，不需要按修饰键：

```
┌───────────────────────────────┐
│░░░░░ 上 25%：插入到本行之前 ░░│  → 排序
├───────────────────────────────┤
│                               │
│      中 50%：并入本行         │  → 分组
│                               │
├───────────────────────────────┤
│░░░░░ 下 25%：插入到本行之后 ░░│  → 排序
└───────────────────────────────┘
```

这是文件管理器几十年验证过的交互（拖到文件夹之间 vs 拖到文件夹上），无需教学。

### 各种组合的语义

| 拖动 | 落点 | 结果 |
|---|---|---|
| 窗口 → 窗口中部 | 中 | **新建组**，包含这两个窗口，位置取被落目标的位置 |
| 窗口 → 组中部 | 中 | 加入该组，追加到成员末尾 |
| 窗口 → 行间 | 上/下 | 纯排序 |
| 组 → 行间 | 上/下 | 整组移动 |
| 组 → 组中部 | 中 | **合并两个组** |
| 组内成员 → 拖出到一级列表行间 | 上/下 | **移出组**，成为独立槽位 |
| 组内成员 → 组内其它位置 | 上/下 | 组内排序 |

### 辅助规则

- 组只剩 1 个成员时**自动解散**，成员升级为一级槽位
- 拖动过程中按住 `Shift` **强制排序**、按住 `Ctrl` **强制分组**，覆盖落点判断（给高级用户的逃生通道）
- 一级槽位已满 16 个时，再拖出新槽位要给明确提示（见待定问题 C）

### 落点判定的实现要点

现有 `SelectorWindow.FindNearestCellFromScreen` 只算**最近的行中心**，拿不到"行内相对位置"。
需要改成：命中测试找到行 → 用 `PointToScreen` 拿到行的屏幕矩形 → 计算 `(y - top) / height` 落在哪一段。

## 7. Q2：分组的可视化

### 一级列表里的组行

```
┌──────────────────────────────────────────┐
│  1   ▣▣    浏览器                 ⊞ 3  ▸ │   ← 组
│      ▣▣                                  │
├──────────────────────────────────────────┤
│  2   ▣     微信                          │   ← 普通窗口
└──────────────────────────────────────────┘
```

四个视觉信号，冗余设计（任何一个失效都还认得出）：

1. **2×2 图标网格**：组行左侧用最多 4 个成员图标拼成缩略网格，普通行是单个图标
2. **成员数徽标** `⊞ 3`
3. **右侧 `▸`**：暗示"还有下一级"
4. **左侧 2px 强调色竖条** + 略深的行背景

### 拖动时的落点反馈

| 落点 | 反馈 |
|---|---|
| 行间（排序） | 行与行之间画一条 2px 强调色**插入线**，两端带小圆点 |
| 行中（分组） | 目标行整体套一圈 2px 强调色**圆角描边** + 背景提亮，ghost 上叠一个 `⊞` 角标 |
| 非法落点 | ghost 变半透明 + `🚫` 角标 |

现有的 `DragGhostAdorner.cs` / `ShowDragGhost` 已经有 ghost 窗口，扩展它即可。

### Level1 的视觉

- 顶部面包屑 `1 ▸ 浏览器`，右侧淡色提示 `Esc 返回`
- 列表整体左缩进 12px，配一条竖直的组色带，强化"我在里面"的层级感
- 进入/返回加 120ms 的横向滑动动画（进入向左推，返回向右推），让层级变化被感知到

## 9. 分阶段实施

每个阶段自身可编译、可运行、可验证，不憋大招。

### P1 — 键位收缩到 16 键（半天）
- 改 `KeyMap`、`MaxPerPage`
- 列表渲染不变，仅标签变化
- **验收**：Alt+Tab 唤起后，`1234qwerasdfzxcv` 能切到对应窗口；第 17 个窗口需翻页

### P2 — 数据层（1 天）
- `LayoutModels` / `LayoutStore` / `LayoutResolver`
- 先不接 UI，写**单元测试**覆盖：同进程自动折叠、新窗口安置、组只剩 1 人自动解散、槽位溢出
- **验收**：给定一组 `WindowInfo` + `layout.json`，解析出的槽位树符合预期（可脱离 UI 跑）

### P3 — 两级键盘导航（1 天）
- `SelectorViewModel` 加层级状态
- `HandleVk` 分派；`Esc` 逐级回退；面包屑
- 组暂时只来自 P2 的自动折叠，还不能手动建组
- **验收**：按 `1` 进组、再按 `1` 切窗口；组内按 `Esc` 回到一级；一级按 `Esc` 关闭

### P4 — 可视化（1 天）
- 组行模板：2×2 图标网格、成员数徽标、`▸`、色带
- Level1 的缩进 + 面包屑 + 滑动动画
- **验收**：一眼能区分组行和窗口行

### P5 — 拖动分组（1.5 天）
- 落点分区判定
- 插入线 / 描边两种反馈
- 七种拖放组合的语义
- 写回 `LayoutStore`
- **验收**：逐条走一遍第 6 节的表格

### P6 — 收尾
- 从旧 `rules.json` 迁移（只保留排除规则，布局重建）
- `README` / `design.md` 更新
- 溢出、空组、全部窗口关闭等边界

## 10. 待定问题（需要你拍板）

### A. 要不要窗口级的固定位置？
第 5 节推荐"组锚定进程、组内按 z-order"。好处是永不漂移，代价是做不到
"这个具体的 VS Code 窗口永远在第 3 位"。

如果要窗口级固定，就得引入标题模式匹配，而标题是会变的——上一轮的失败用例正是这个：
VS Code 改了标题后，仍能匹配的微信就升到了第 1 位。
**✅ 已定：按推荐方案做，不追求窗口级固定。** 身份只锚定 `ProcessName`；`SlotEditor.MoveOutOfGroup` 对单进程组返回 `null`，调用方给提示。

### B. 同进程多窗口，默认自动折叠成组吗？
- 折叠：一级列表更短、更稳定，但单窗口的应用和多窗口的应用行为不一致（一个直达一个要两下）
- 不折叠：行为统一，但 16 个槽位很快被 VS Code 之类占满

**✅ 已定：折叠，阈值可配** —— `Layout.AutoGroupThreshold`，默认 2，设成 99 等于关闭自动分组。

### C. 一级槽位超过 16 个怎么办？
1. 翻页（`PageDown`/`PageUp`），沿用现在的做法
2. 第 16 格自动变成"更多…"组，装下所有溢出的
3. 溢出的直接不显示

**✅ 已定：方案 2** —— 第 16 格变「更多…」组。翻页整个移除。溢出组在 ToDocument 时会被摊平，不会固化成真的组。

### D. 搜索框和索引键的冲突
现在钩子吞掉所有索引键，搜索框打不进字。可选：
1. 维持现状，搜索基本是摆设
2. 搜索框非空时，索引键让位给文本输入，改用 `Enter` / `↑↓` 选择
3. 加一个显式的搜索模式（`/` 进入，`Esc` 退出）

**✅ 已定：方案 3** —— `/` 进入、`Esc` 退出。进入搜索时通过 `SearchModeChanged` 通知 App
让钩子整体放行索引键，否则搜索框一个字都打不进去。搜索结果是跨组的扁平列表。

### E. 组需要命名吗？
自动折叠的组可以直接用进程名（"Visual Studio Code"）。手动建的组需要用户起名，
就得有个重命名入口（Level1 里按 `F2`？）。
**✅ 已定：自动生成** —— LayoutResolver.AutoName：单进程用进程名去 .exe，多进程用「首进程 +N」。目标本来是组时合并沿用原名。重命名留待后续。

## 11. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 拖动落点分区在 144px 行高下手感不好 | 中 | P5 先做可调参数，实测再定三段比例 |
| 自动折叠让用户找不到窗口 | 中 | 组行显示成员数；搜索做成**跨层级扁平搜索** |
| `layout.json` 与实际窗口长期漂移（应用卸载等） | 低 | 解析时丢弃匹配不上的条目，写回时自动清理 |
| 一次性改动面过大 | 高 | 严格按 P1–P6 分阶段，每阶段可独立回滚 |

## 12. 这个计划**没有**解决的

- 窗口级的绝对固定位置（见待定问题 A）
- 跨虚拟桌面的分组
- 组的嵌套（只做两级，不做三级及以上）
